# 総務省Excel 財政データインポート設計

## 目的

**管理者（CivicTechEzo運営メンバー）が**、北海道内自治体の財政データを手作業で入力・変換する手間を解消し、年度を指定するだけで総務省公開の決算データをDBに取り込めるようにするため。

---

## スコープ

- 総務省「市町村別決算状況調べ」のExcelファイルからデータを取得し、`FiscalYearSettlement` テーブルにインポートする
- admin画面から年度を指定してプレビュー→確認→インポートの操作フロー
- 初期データ投入用のCLIスクリプト（過去10年分の一括取り込み）
- 対象: 北海道内の自治体のみ（団体コード `01xxx`）

---

## データソース

### 総務省「市町村別決算状況調べ」

- 一覧ページ: `https://www.soumu.go.jp/iken/kessan_jokyo_2.html`
- 年度ごとのページ: `https://www.soumu.go.jp/iken/zaisei/{年度コード}_shichouson.html`
  - 令和: `r01`, `r02`, ... `r06`
  - 平成: `h15`, `h16`, ... `h30`
- 各ページに5つのExcelファイルがぶら下がる（`/main_content/{番号}.xlsx`）

### ファイル構成（年度ごとに5ファイル）

| # | 内容 | 対応するスキーマ列群 |
|---|------|---------------------|
| (1) | 調査票 | 財政指標、基金残高、地方債残高、人口 |
| (2) | 歳入決算額 | `rev_*`（歳入） |
| (3) | 目的別歳出決算額 | `exp_assembly` 〜 `exp_purpose_total` |
| (4) | 性質別歳出決算額 | `exp_personnel` 〜 `exp_nature_total` |
| (5) | 地方債現在高 | `local_bond_balance`（補完用） |

### ExcelファイルURLの特性

- ファイル番号（`/main_content/001061670.xlsx` 等）は年度ごとに異なり規則性がない
- ただし同一年度の5ファイルは連番（(1)のIDがわかれば +1, +2... で(2)〜(5)が取れる）
- **年度ページのHTMLをパースしてxlsxリンクを抽出する**方式で対応する（cheerio使用）

### Excelの構造

- 1ファイルに**全国の全市町村**が含まれる（約1,700行）
- 先頭数行がヘッダー（複数行にまたがるマージセル）、その後に自治体ごとの行
- 各行に「団体コード」列があり、`01xxx` でフィルタすることで北海道分を抽出可能
- 金額の単位は千円

## Bounded Context の配置

既存の `data-import` コンテキストを再利用する。

**理由**: 旧プロジェクト（政治資金）のMFクラウドCSV取り込みがこのコンテキストにあるが、本プロジェクトではMFクラウドは不要。data-importコンテキストの責務は「外部データの取り込み」であり、データソースが変わるだけで責務は同じ。旧コードは段階的に置き換える。

## 処理フロー

### admin画面からのインポート

```
[admin画面: 年度選択]
  │
  ▼ action: fetch-settlement-preview
  │
  ├─ 1. SoumuPageScraper: 年度ページをfetch → ExcelファイルURLを抽出
  ├─ 2. SoumuExcelParser: 5つのExcelをダウンロード → パース
  ├─ 3. ExcelToSettlementMapper: 生データ → SettlementPreview[] に変換（北海道のみ）
  ├─ 4. SettlementValidator: バリデーション
  │     ├─ 数値整合性チェック（歳入合計 = 各款の合計 等）
  │     ├─ 必須項目チェック
  │     └─ 登録済みデータとの重複チェック
  │
  ▼ [admin画面: プレビュー表示]
  │   ├─ 取り込み対象の自治体数
  │   ├─ insert / update / skip の内訳
  │   ├─ warnings（合計値不一致等）
  │   └─ errors（致命的な問題）
  │
  ▼ action: import-settlement-data（ユーザー確認後）
  │
  ├─ 5. SaveSettlementUsecase: upsert実行
  └─ 6. revalidateTag でキャッシュ無効化
```

### CLI による初期データ一括投入

```
pnpm settlement:import --from r03 --to r06
```

- admin画面と同じUsecase層を共有する
- `scripts/import-settlement.ts` として配置
- 引数で年度範囲を指定、確認プロンプト付き

## 主要コンポーネントの仕様

### SoumuPageScraper（Infrastructure）

**責務**: 総務省の年度ページHTMLをfetchし、ExcelファイルのURLを抽出する

- 入力: 年度コード（例: `"r06"`）
- 出力: `{ survey: string; revenue: string; expensePurpose: string; expenseNature: string; localBond: string }` （各ExcelのURL）
- 年度コードから年度ページURLを組み立て: `https://www.soumu.go.jp/iken/zaisei/{code}_shichouson.html`
- cheerioでHTMLをパース、市町村決算セクションの `.xlsx` リンクを抽出
- 5つのリンクが取得できない場合はエラー

### SoumuExcelParser（Infrastructure）

**責務**: Excelファイルをダウンロードしてパースし、生データの行配列を返す

- 入力: ExcelファイルのURL
- 出力: 行データの配列（ヘッダーマッピング済み）
- xlsxライブラリ（SheetJS）を使用してパース
- ヘッダー行の位置検出（「団体コード」列を探す）
- 北海道フィルタ: 団体コードが `01` で始まる行のみ抽出

### ExcelToSettlementMapper（Domain Service）

**責務**: パースされたExcelの行データを `SettlementPreview` ドメインモデルにマッピングする

- Excel列名 → `FiscalYearSettlement` のフィールド名の対応を定義
- 金額は千円単位のためそのままBigIntに変換
- 財政指標（比率・指数）はDecimalに変換
- マッピングできない列はwarningとして記録

### SettlementValidator（Domain Service）

**責務**: マッピング後のデータの妥当性を検証する

検証項目:
- **数値整合性**: `revTotal` と各歳入科目の合計が一致するか（許容誤差あり）
- **必須項目**: 団体コード、年度、歳入合計、歳出合計が存在するか
- **重複チェック**: 同一 `municipalityId` + `fiscalYear` の既存データの有無 → insert / update / skip の判定
- **団体コードの存在**: シードデータの `municipalityCode` に対応するレコードが `Municipality` テーブルに存在するか

### SettlementPreview（Domain Model）

```
SettlementPreview {
  municipalityCode: string      # 団体コード
  municipalityName: string      # 団体名（表示用）
  fiscalYear: number            # 年度
  status: "insert" | "update" | "skip" | "invalid"
  data: Record<string, bigint | number>  # FiscalYearSettlement のフィールド値
  errors: ValidationError[]     # 致命的エラー
  warnings: ValidationError[]   # 警告（処理続行可能）
}
```

## エラーハンドリング

### エラーコード定義

| コード | severity | 意味 |
|--------|----------|------|
| `IMPORT_FETCH_FAILED` | error | 総務省ページ/Excelの取得失敗 |
| `IMPORT_PARSE_FAILED` | error | Excelパース失敗 |
| `IMPORT_INVALID_YEAR_CODE` | error | 不正な年度コード |
| `IMPORT_MUNICIPALITY_NOT_FOUND` | error | 団体コードに対応するMunicipalityが未登録 |
| `IMPORT_REQUIRED_FIELD_MISSING` | error | 必須フィールドが欠損 |
| `IMPORT_TOTAL_MISMATCH` | warning | 合計値と内訳の不一致（許容誤差内ならwarning） |
| `IMPORT_ALREADY_EXISTS` | warning | 同一年度・自治体のデータが既に存在（上書き確認） |
| `IMPORT_COLUMN_NOT_MAPPED` | warning | マッピングできないExcel列がある |

### エラー型

```
ValidationError {
  path: string          # エラー箇所（例: "札幌市.revTotal"）
  code: string          # 上記エラーコード
  message: string       # 日本語メッセージ
  severity: "error" | "warning"
}
```

- errors がある自治体行は `status: "invalid"` となりインポート対象外
- warnings のみの行はプレビュー画面で黄色表示し、ユーザー確認の上インポート可能

## 年度コードの管理

### 年度コードと西暦の対応

| 年度コード | 和暦 | 西暦（fiscalYear） |
|-----------|------|-------------------|
| h27 | 平成27年度 | 2015 |
| h28 | 平成28年度 | 2016 |
| h29 | 平成29年度 | 2017 |
| h30 | 平成30年度 | 2018 |
| r01 | 令和元年度 | 2019 |
| r02 | 令和2年度 | 2020 |
| r03 | 令和3年度 | 2021 |
| r04 | 令和4年度 | 2022 |
| r05 | 令和5年度 | 2023 |
| r06 | 令和6年度 | 2024 |

### 変換ロジック（Domain Model）

年度コード ↔ 西暦の変換はドメインモデルとして定義する。`FiscalYearCode` モデルに、コードから西暦への変換、西暦からコードへの逆変換、コードのバリデーションを持たせる。

---

## 団体コードの対応

### Excel側の団体コード

Excelの「団体コード」列は **5桁**（チェックディジットなし、例: `01100` = 札幌市）。

### DB側の municipalityCode

シードデータの `municipalityCode` は **6桁**（チェックディジットあり、例: `011002` = 札幌市）。

### マッピング方法

Excel側5桁コードの先頭5桁と、DB側6桁コードの先頭5桁を照合する。Municipality テーブルから全北海道自治体を取得し、`municipalityCode.slice(0, 5)` でルックアップテーブルを構築する。
