# 旧コード削除と流用コード書き換え設計

## 目的

**開発者が**、旧プロジェクト（政治資金可視化）のコードが残存することによる typecheck エラー（webapp 38件 + admin 427件）と可読性の低下を解消するため。

具体的には:
1. typecheckが通る状態にする（`--no-verify` なしで push できるようにする）
2. 旧モデル（Transaction, PoliticalOrganization, Counterpart, Donor 等）への参照をコードベースから除去し、新モデル（Municipality, FiscalYearSettlement）ベースの構造にする
3. 流用可能なコード（サンキー図パイプライン等）は新データモデル向けに書き換えて活かす

---

## 現状のエラー分類

### webapp（38件）

すべて `public-finance` コンテキストの旧コードに起因:

| 原因 | ファイル数 | 内容 |
|------|-----------|------|
| `PoliticalOrganization` Prismaモデル消失 | 1 | `prisma-political-organization.repository.ts` |
| `Transaction` Prismaモデル消失 | 2 | `prisma-transaction.repository.ts`, `prisma-balance-sheet.repository.ts` |
| `PL_CATEGORIES`/`BS_CATEGORIES` 未export | 3 | 上記 + `display-transaction.ts`, `CategoryFilter.tsx`, `TransactionTableRow.tsx` |

### admin（427件）

| 原因 | エラー数（概算） | 内容 |
|------|-----------------|------|
| BigIntリテラル（tsconfig target ES2017） | ~330 | `excel-to-settlement-mapper.ts` + テスト |
| `PL_CATEGORIES`/`BS_CATEGORIES`/`CASH_ACCOUNTS` 未export | ~30 | 旧コンポーネント・サービス 11ファイル |
| Prismaモデル消失（Counterpart, Donor, Transaction等） | ~50 | reportコンテキスト、sharedコンテキストのリポジトリ実装 |
| `xlsx`/`cheerio` 未インストール | ~5 | `soumu-excel-parser.ts`, `soumu-page-scraper.ts` |
| その他（型不整合、引数不一致） | ~12 | `import-settlement-data.ts`, `SettlementPreviewData` キャスト |

---

## 対応の全体方針

3つのステップで段階的に対応する:

```
Step 1: 設定修正（admin の新コードのエラーを解消）
  ↓
Step 2: 旧コード一括削除（エラーの根本原因を除去）
  ↓
Step 3: 流用コードの書き換え（新データモデルで typecheck を通す）
```

Step 1 → Step 2 で typecheck が通る状態になり、Step 3 でフェーズ2-1（コア可視化）への接続が完了する。

### 3-1. category-aggregation.ts — BalanceInfo の書き換え

**現在の BalanceInfo:**
- `previousYearBalance` — 前年度末の現金残高（旧 BalanceSnapshot から取得）
- `currentYearBalance` — 当年度末の現金残高（同上）
- `liabilityBalance` — 負債残高（旧 BalanceSheet から取得）

**書き換え後の BalanceInfo:**
- `previousYearBalance` → `revCarryover`（FiscalYearSettlement の繰越金フィールド。歳入内訳に既に含まれるため、adjustWithBalance での加算は不要になる可能性がある。サンキー図で二重計上にならないよう注意）
- `currentYearBalance` → 歳入合計 - 歳出合計（FiscalYearSettlement の `revTotal` - `expPurposeTotal`）
- `liabilityBalance` → 自治体財政の文脈では「未払費用」ではなく、不要になる可能性が高い。adjustWithBalance の friendlyモード分岐を簡略化

**変更箇所:**
- `BalanceInfo` interface の定義
- `adjustWithBalance` メソッドの引数と内部ロジック
- 呼び出し元（get-sankey-aggregation-usecase）での引数構築

### 3-2. get-sankey-aggregation-usecase.ts — リポジトリ差し替え

**現在の依存（4つのリポジトリ）:**
- `ITransactionRepository` → 削除
- `IPoliticalOrganizationRepository` → 削除
- `IBalanceSnapshotRepository` → 削除
- `IBalanceSheetRepository` → 削除

**書き換え後の依存（2つのリポジトリ）:**
- `IMunicipalityRepository` — slug から Municipality を取得
- `IFiscalSettlementRepository` — municipalityId + fiscalYear から FiscalYearSettlement を取得

FiscalYearSettlement は歳入・歳出が全フィールド集計済みのため、旧コードの「Transaction を集計して CategoryAggregation を作る」処理が不要になる。代わりに FiscalYearSettlement のフィールドを `REVENUE_CATEGORIES`/`EXPENSE_PURPOSE_CATEGORIES`（`shared/accounting/account-category.ts`）とマッピングして CategoryAggregation を直接構築する。

**変更箇所:**
- constructor の引数を2つのリポジトリに変更
- `GetSankeyAggregationParams` の `categoryType` を `"purpose"` | `"nature"` に変更（旧 "political-category" / "friendly-category" の概念が変わる。目的別歳出 / 性質別歳出の切替になる）
- execute メソッド内で FiscalYearSettlement → CategoryAggregation への変換ロジックを実装（ドメインサービスとして切り出すのが妥当）

### 3-3. 新規リポジトリの作成

#### IMunicipalityRepository（domain/repositories/）

必要なクエリ:
- `findBySlug(slug: string)` — 単一自治体の取得
- `findBySlugs(slugs: string[])` — 複数自治体の取得（サンキー図用）
- `findAll()` — 全自治体一覧（自治体選択UI用）

Prisma 実装: `prisma.municipality.findMany()` 等で Municipality テーブルを直接クエリ。

#### IFiscalSettlementRepository（domain/repositories/）

必要なクエリ:
- `findByMunicipalityAndYear(municipalityId: bigint, fiscalYear: number)` — 特定自治体・年度のデータ取得
- `getAvailableYears(municipalityId: bigint)` — 当該自治体で利用可能な年度一覧

Prisma 実装: `prisma.fiscalYearSettlement.findUnique()` 等で FiscalYearSettlement テーブルをクエリ。

### 3-4. 新規ドメインサービスの作成 — FiscalYearSettlement → CategoryAggregation 変換

FiscalYearSettlement のフィールド値を `REVENUE_CATEGORIES` / `EXPENSE_PURPOSE_CATEGORIES` / `EXPENSE_NATURE_CATEGORIES` とマッピングし、CategoryAggregation を構築するドメインサービス。

**入力:** FiscalYearSettlement（BigInt フィールド群）+ 表示モード（目的別 / 性質別）
**出力:** CategoryAggregation（`{ income: CategoryAggregationItem[], expense: CategoryAggregationItem[] }`）

**変換ロジック:**
- `REVENUE_CATEGORIES` の各 `fieldName` に対応する FiscalYearSettlement のフィールド値を `CategoryAggregationItem` に変換（BigInt → number）
- 表示モードに応じて `EXPENSE_PURPOSE_CATEGORIES` または `EXPENSE_NATURE_CATEGORIES` を使用
- 値が 0 の科目はスキップ（サンキー図のノイズ防止）

### 3-5. get-organizations-usecase.ts — Municipality 対応

`IPoliticalOrganizationRepository` → `IMunicipalityRepository` に差し替え。
戻り値の型を `PoliticalOrganization` → Municipality 情報に変更。
`webapp/src/types/organization.ts` の `OrganizationData` 型はそのまま使えるが、Municipality のフィールド名に合わせたマッピングが必要（`orgName` → `name` 等）。

### 3-6. load-top-page-data.ts — 大幅簡略化

**現在（5つの usecase を2段階で並列実行）:**
