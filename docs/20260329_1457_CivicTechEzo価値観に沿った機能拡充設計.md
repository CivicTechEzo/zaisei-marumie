# CivicTechEzo価値観に沿った機能拡充設計

## 目的

**北海道の住民が**、自分のまちの財政状況を「気軽に目にでき、理解できる」状態になるため。

現状のダッシュボードは歳入・歳出のデータを正確に可視化しているが、財政用語や大きな金額の羅列は住民にとって馴染みが薄く、「見てみよう」から「なるほど」→「誰かに伝えたい」→「自分ごとだ」という連鎖が起きにくい。

本設計では、**既存のデータモデル・画面構成を活かし、新規の機能開発工数を最小限に抑えつつ**、CivicTechEzoが大切にする以下の価値連鎖を実現する機能を定義する。

```
見るハードルを下げる → 理解しやすくする → 自然と気づきが生まれる → 共有したくなる → 当事者意識につながる
```

---

## 前提・制約

- 既存データモデル（Transaction, BalanceSnapshot, PoliticalOrganization, SankeyData等）をそのまま活用する
- 既存のダッシュボードページ（`/o/[slug]/[year]`）と取引一覧ページ（`/o/[slug]/[year]/transactions`）をベースに拡張する
- 新規のバックエンド機能（API、usecase等）の追加は最小限とし、既存のloader/usecaseから取得できるデータの**表示・加工**で実現可能な施策を優先する
- 自治体財政の文脈に合わせた文言・用語への変更を含む

---

## 施策一覧と対応する価値連鎖

| # | 施策 | 価値連鎖の段階 | 新規バックエンド工数 |

## 施策1: ひとことサマリー

### 概要

ダッシュボード最上部（CashFlowSectionの上、またはFinancialSummarySectionの直上）に、財政データを自然言語で1〜2文に要約したカードを表示する。数字の羅列を見る前に「なるほど」と思える入口を作る。

### 表示例

> 「札幌市の2025年度の歳出は約1,200億円。最も大きいのは福祉関連で全体の35%を占めています。」

> 「〇〇町の歳入のうち、自主財源（税金など）は32%。残りの68%は国や道からの交付金に頼っています。」

### データソース

- 既存の`loadTopPageData`で取得されるSankeyData（friendly）を使用
- 収入総額・支出総額はFinancialSummarySectionと同じ計算ロジック（`calculateFinancialData`）を流用
- カテゴリ別の金額はSankeyDataのnodes/linksから取得可能（最大カテゴリの特定）

### 設計方針

- サーバーコンポーネントとして実装し、SankeyDataを受け取ってテンプレートベースで文章を生成する
- LLMは使わない。テンプレートに数値を埋め込む方式（例: `${orgName}の${year}年度の歳出は${expense}。最も大きいのは${topCategory}で全体の${percentage}%です。`）
- テンプレートは複数パターン用意し、データの特徴（収支バランス、最大カテゴリの偏り等）に応じて出し分ける

### コンポーネント配置

```
webapp/src/client/components/top-page/
  └── SummaryCard.tsx（新規・サーバーコンポーネント）
```

ダッシュボードページ（`page.tsx`）にて、`CashFlowSection`の直前に配置する。

### テンプレート設計

以下の要素を組み合わせて文章を生成する:

| 要素 | 取得方法 |
|------|---------|
| 組織名 | `currentOrganization.displayName` |
| 年度 | URLパラメータ `year` |
| 歳入総額 | SankeyData → `calculateFinancialData().income` |
| 歳出総額 | SankeyData → `calculateFinancialData().expense` |
| 最大歳出カテゴリ名 | SankeyData.links のうちexpense系で最大のもの |
| 最大カテゴリの割合 | 最大カテゴリ金額 / 歳出総額 × 100 |
| 収支（黒字/赤字） | income - expense の正負 |

テンプレートパターン例:

1. **基本パターン**: 「{orgName}の{year}年度の支出は{expense}。最も多いのは{topCategory}（{percentage}%）です。」
2. **収支強調パターン**（赤字の場合）: 「{orgName}の{year}年度は、収入{income}に対し支出{expense}で、{deficit}の赤字です。」
3. **カテゴリ偏り強調パターン**（1カテゴリが50%超の場合）: 「{orgName}の支出の半分以上は{topCategory}に充てられています。」

## 施策2: 用語の平易化（用語翻訳マッピング）

### 概要

既存の「詳細の区分」「法律上の区分」タブの仕組みを拡張し、財政用語を日常的な言葉に置き換えるマッピングを導入する。自治体財政の文脈では、住民にとって馴染みのない用語が多いため、見るハードルを下げる効果が大きい。

### 設計方針

- 翻訳マッピングは静的な定数オブジェクトとして定義する（DBやAPIは不要）
- 既存の`PL_CATEGORIES`（`shared/accounting/account-category.ts`）の構造を参考に、表示用ラベルを追加する
- サンキー図のノードラベル、FinancialSummaryCard、取引一覧のカテゴリ名に適用する

### マッピング定義

```
webapp/src/client/lib/
  └── friendly-term-map.ts（新規）
```

| 財政用語 | 平易な表現 | 補足 |
|---------|-----------|------|
| 地方交付税交付金 | 国からの仕送り | |
| 地方税 | 住民が納めた税金 | |
| 国庫支出金 | 国からの補助金 | |
| 地方債 | 自治体の借金 | |
| 公債費 | 借金の返済 | |
| 人件費 | 職員の給料 | |
| 扶助費 | 福祉・医療の支援 | |
| 普通建設事業費 | 道路・建物の工事 | |
| 物件費 | 備品・サービスの購入 | |
| 繰出金 | 他の会計への資金移動 | |
| 補助費等 | 団体・事業への補助 | |
| 維持補修費 | 施設の修理・メンテナンス | |

### 適用箇所

1. **サンキー図のノードラベル**: `SankeyChart.tsx`のCustomLabelsLayerで、ラベル描画時にマッピングを適用
2. **FinancialSummaryCard**: カテゴリ名表示に適用
3. **取引一覧ページ**: カテゴリフィルタの選択肢と表中のカテゴリ名に適用
4. **ひとことサマリー（施策1）**: テンプレート内のカテゴリ名に適用

### 切替UI

- 既存の「詳細の区分」「法律上の区分」タブに「かんたんな言葉」タブを追加する案もあるが、まずはデフォルトで平易な表現を使い、元の用語はツールチップやカッコ書きで補足する形を推奨
- 理由: タブが増えると選択の負荷が上がり「見るハードルを下げる」に反する

## 施策3: 住民1人あたり換算表示

### 概要

歳出の各カテゴリ金額を「住民1人あたり」に換算して表示するトグルを追加する。億単位の金額は生活感覚から遠いが、1人あたりに換算することで日常の支出と比較可能になり、理解と気づきを促す。

### データソース

- 歳出データ: 既存のSankeyData（各カテゴリの金額）
- 人口データ: **PoliticalOrganizationモデルへの追加が必要**

### PoliticalOrganizationモデルへの人口データ追加

現在のスキーマ:
```
PoliticalOrganization {
  id, displayName, slug, orgName, tenantId, ...
}
```

追加するフィールド:
- `population: Int?` — 住民基本台帳ベースの人口

追加方法:
- Prismaスキーマに`population`フィールドを追加
- adminの管理画面から手動入力、またはシードデータで投入
- 北海道内自治体の人口は総務省統計局の公開データから取得可能

### 表示方針

- FinancialSummarySectionに「1人あたり」トグルボタンを追加
- トグルON時: 各金額を`金額 / population`で割って表示（円単位、千円単位）
- サンキー図のラベルにも1人あたり金額を併記（トグル連動）
- 人口データがない組織の場合はトグルを非表示にする

### 表示例

| カテゴリ | 総額 | 1人あたり |
|---------|------|----------|
| 福祉・医療の支援 | 420億円 | 約21万円 |
| 職員の給料 | 180億円 | 約9万円 |
| 道路・建物の工事 | 95億円 | 約4.8万円 |
| 借金の返済 | 85億円 | 約4.3万円 |

### コンポーネント設計

- `FinancialSummarySection`を`"use client"`化（既にCashFlowSection内でclient-only）
- トグル状態はCashFlowSectionのstateで管理し、FinancialSummarySectionとSankeyChartに伝搬
- populationデータはloadTopPageDataの戻り値に含める（organizationデータに付随）

## 施策4: 経年変化ハイライト

### 概要

前年度との比較で大きく変化した項目を自動検出し、ダッシュボード上で目立たせる。変化があるから「なぜ？」が生まれ、気づきにつながる。

### データソース

- 既存の年度切替機能（`VALID_YEARS = [2025, 2026]`）で複数年のSankeyDataを取得可能
- `loadTopPageData`を2年分呼ぶ、または前年度データも併せて取得するようloaderを拡張

### 設計方針（最小工数アプローチ）

ダッシュボードページで現在年度のデータを取得する際、前年度のSankeyDataも並行取得する。取得は既存の`loadTopPageData`をもう1回呼ぶだけで実現可能。

### 変化検出ロジック

サーバーコンポーネントまたはドメインモデルとして実装:

1. 両年度のSankeyDataからカテゴリ別金額を抽出
2. カテゴリごとに前年比（増減率）を計算
3. 閾値（例: ±20%以上、または絶対額で一定以上）を超えた項目を「注目の変化」として抽出
4. 増減率の大きい順にソートし、上位3件を表示

### 表示箇所

- CashFlowSectionの直下、またはMonthlyTrendsSectionの直前に「前年度からの変化」カードとして配置
- 変化がない場合（初年度データのみの場合）は非表示

### 表示例

> **前年度からの注目の変化**
> - 福祉関連: +12%（前年 380億 → 今年 420億）
> - 道路工事: -18%（前年 115億 → 今年 95億）
> - 人件費: +3%（大きな変化なし → 非表示）

## 施策5: SNSシェア用OGP対応

### 概要

ダッシュボードのURLがSNSでシェアされた際に、財政データのサマリーが画像として表示されるよう、動的OGP画像を生成する。「気づき」が「共有」に変わるための仕組み。

### 現状

- 静的な`/social/og_image.png`（1200x630）が全ページ共通で使用されている
- 組織名や年度に応じた動的なOGP画像は未実装

### 設計方針

Next.js App RouterのOG Image Generation（`opengraph-image.tsx`）を使い、組織・年度ごとに動的にOGP画像を生成する。

### OGP画像の内容

1行目: 組織名 + 年度
2行目: ひとことサマリー（施策1と同じテンプレート）
3行目: 収入・支出・収支の3つの数字
背景: ブランドカラー（#64D8C6〜#BCECD3のグラデーション）

### ファイル配置

```
webapp/src/app/o/[slug]/[year]/
  └── opengraph-image.tsx（新規）
```

Next.jsの規約により、このファイルを配置するだけで`/o/[slug]/[year]`のOGP画像が自動的にこの動的画像に差し替わる。

### データ取得

- `opengraph-image.tsx`内で`loadTopPageData`を呼び、SankeyDataから収入・支出・収支を計算
- 既存のloaderとキャッシュをそのまま活用するため、パフォーマンスへの影響は最小限

## 施策6: サイト全体の自治体財政コンテキスト化

### 概要

現在のサイトは政治資金の文脈（「チームみらい」「政治資金」「政治団体」等）で構成されている。自治体財政まる見えプロジェクトとして、サイト全体の文言・メタデータ・セクション内容を自治体財政の文脈に更新する。

### 対象箇所と変更内容

#### メタデータ（`layout.tsx`）

| 項目 | 現在 | 変更後 |
|------|------|--------|
| title | 「みらい まる見え政治資金 - チームみらいの政治資金をオープンに」 | 「自治体財政まる見え - 北海道の自治体財政をオープンに」 |
| description | 「チームみらいの政治資金の流れを透明性を持って公開する…」 | 「北海道内自治体の財政データを住民にわかりやすく公開する…」 |
| OGP title/description | 同上 | 同上 |

#### CashFlowSection

| 項目 | 現在 | 変更後 |
|------|------|--------|
| CardHeader title | 「収支の流れ」 | 「歳入・歳出の流れ」または「お金の流れ」 |
| CardHeader subtitle | 「どこからお金を得て、何に使っているか」 | そのまま（適切） |
| organizationName fallback | 「未登録の政治団体」 | 「未登録の自治体」 |

#### ExplanationSection

政治資金の説明文を自治体財政の説明文に全面書き換え:

1. **自治体財政まる見えについて**: プロジェクトの説明（CivicTechEzo発、オープンソース、住民向け）
2. **データの出典**: 各自治体が公開している決算書・予算書に基づく旨
3. **免責事項**: データの正確性に関する免責（現在と同様の構成）

#### AboutSection

「チームみらいについて」→「CivicTechEzoについて」に変更。団体の説明とSNSリンクを更新。

#### TransparencySection

| 項目 | 現在 | 変更後 |
|------|------|--------|
| title | 「党首もこれを見て、お金をやりくりしています👀」 | 自治体財政の文脈に合った文言（例: 「あなたのまちのお金の使いみち、見てみませんか？」） |

#### Footer

- テキストリンクを自治体財政の文脈に更新（「寄附で応援する」「チームみらい党員になる」→ 削除またはCivicTechEzo関連リンクに変更）
- SNSリンクをCivicTechEzoのものに更新
- コピーライトを更新

#### generateMetadata（`page.tsx`）

| 項目 | 現在 | 変更後 |
|------|------|--------|
| title | `${org.displayName} - みらいまる見え政治資金` | `${org.displayName} - 自治体財政まる見え` |

### 変更の進め方

この施策はコード変更量は多いが、すべて静的な文言の差し替えであり、ロジック変更を伴わない。他の施策と独立して着手できる。

## 実装順序

以下の順序で着手することを推奨する。依存関係と効果のバランスを考慮している。

```
施策6（コンテキスト化）  ← 他施策と独立。最初に着手し、サイト全体の方向性を確定
  ↓
施策2（用語の平易化）    ← 施策6と合わせて実施するのが自然
  ↓
施策1（ひとことサマリー） ← 施策2の用語マッピングを使用
  ↓
施策5（OGP対応）         ← 施策1のテンプレートを流用
  ↓
施策3（1人あたり換算）   ← スキーマ変更が必要なため後半
  ↓
施策4（経年変化）        ← 複数年データが揃ってから
```

## アーキテクチャ整合性

- 新規コンポーネントはすべてサーバーコンポーネント（SummaryCard等）またはクライアントコンポーネント内の表示ロジック変更であり、既存のレイヤー構造に影響しない
- データ取得は既存のloader（`loadTopPageData`）を経由し、直接のリポジトリ・usecase呼び出しは行わない
- 用語マッピング（`friendly-term-map.ts`）はクライアント側の表示変換であり、ドメイン層には影響しない
- 施策3の人口データ追加のみ、Prismaスキーマ変更とloaderの軽微な拡張が必要
- 施策5のOGP画像生成はNext.jsの規約に沿った配置であり、アーキテクチャの逸脱はない
