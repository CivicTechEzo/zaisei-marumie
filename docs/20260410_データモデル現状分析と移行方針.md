# データモデル現状分析と移行方針

## 目的

現在のPrismaスキーマ（政治資金可視化アプリ由来）を棚卸しし、自治体財政可視化に向けて各モデルを「維持」「変更」「削除」「新規作成」のいずれに分類する。フェーズ1-1（データモデル設計）の入力ドキュメントとなる。

---

## 現行モデル一覧と判定

### 維持: そのまま使えるモデル

#### User / UserTenantMembership / Tenant

```prisma
model User {
  id, authId, email, role, createdAt, updatedAt
  tenantMemberships UserTenantMembership[]
}

model Tenant {
  id, name, slug, description, createdAt, updatedAt
  politicalOrganizations, memberships, ...
}

model UserTenantMembership {
  id, userId, tenantId, role, createdAt, updatedAt
}
```

**判定: 維持（Tenantは1つ固定で運用）**

- 認証・マルチテナント基盤はドメインに依存しない汎用的な構造
- adminの認証フロー（Supabase Auth → User → Tenant）がそのまま使える
- Tenantの `relations` から政治資金系モデル（`counterparts`, `donors`）の参照を削除する必要があるが、モデル自体は変更不要

**Tenantの運用方針:**

元のmarumieではTenant=党（自民党、民主党等）を表し、各党が自分のデータだけを管理するSaaS型マルチテナント構造だった。本プロジェクトでは「CivicTechEzoが北海道の全自治体データを一括管理して公開する」形のため、マルチテナントの必要性はない。

- Tenantは1つ（CivicTechEzo）に固定して運用する
- CTE内の複数人でadminを管理する場合は、同一Tenant内でUserTenantMembershipのrole（owner/admin/editor）で権限を分ける
- 仕組み自体は残す（削除しない）。削除のコスト（auth周りの改修が広範囲に及ぶ）に対してメリットが薄く、将来他地域のCivicTech団体が参加する可能性に備えられる

### 変更: 拡張または改名が必要なモデル

#### PoliticalOrganization → 自治体エンティティとして拡張

```prisma
// 現在
model PoliticalOrganization {
  id, displayName, description, slug, orgName
  tenantId
  balanceSnapshots, reportProfiles, transactions  // ← 政治資金系のrelation
}
```

**判定: 変更（フィールド追加 + relation差し替え）**

**理由:**

- `displayName`, `slug`, `tenantId` は自治体でもそのまま使える（例: slug="sapporo", displayName="札幌市"）
- webappのloader/page.tsxが `PoliticalOrganization` のslugでルーティングしており、モデルを分離するとこれらの上流すべてに変更が波及する
- 「政治団体と自治体を1モデルに混在させる」懸念はあるが、実運用上このアプリで政治団体データを扱うことはないため、実質的に自治体専用モデルとして扱える
- テーブル名（`political_organizations`）やモデル名の改名は、マイグレーションのリスクに対してメリットが小さいため後回しでよい

**追加が必要なフィールド:**

| フィールド | 型 | 用途 |
|-----------|---|------|
| `municipalityCode` | `String @unique` | 全国地方公共団体コード（6桁）。データ取り込み時の突合キー |
| `municipalityType` | `MunicipalityType` enum | 道 / 市 / 町 / 村。表示やフィルタリングに使用 |
| ~~`population`~~ | — | 人口は年度ごとに変動するため、FiscalYearSettlementに持たせる（決算カードにも年度ごとの人口が記載されている）。1人あたり歳出の経年比較にも対応できる |
| `area` | `Float?` | 面積（km²）。人口密度の算出に使用 |

**削除が必要なrelation:**

- `transactions` → Transactionモデル削除に伴い消滅
- `reportProfiles` → OrganizationReportProfile削除に伴い消滅
- `balanceSnapshots` → 後述（BalanceSnapshotの扱いによる）

**追加するrelation:**

- `fiscalYearSettlements` → 新規モデル（後述）

#### BalanceSnapshot → 用途を再定義

```prisma
// 現在
model BalanceSnapshot {
  id, politicalOrganizationId, snapshotDate, balance, createdAt, updatedAt
}
```

**判定: 削除候補（FiscalYearSettlementに統合）**

**理由:**

- 政治資金では「日次の現金残高」を記録する用途だった
- 自治体財政では「積立金現在高」「地方債現在高」を年度単位で保持する必要がある
- これらは決算カードの一項目として取り込まれるため、FiscalYearSettlement（後述）のフィールドとして保持するのが自然
- 日次の残高推移は自治体財政では不要

### 削除: 自治体財政で不要なモデル

#### Transaction

```prisma
model Transaction {
  // 個別取引の複式簿記（借方・貸方）
  debitAccount, debitAmount, creditAccount, creditAmount, ...
  transactionType: income | expense | non_cash_journal | offset_income | offset_expense
}
```

**判定: 削除**

**理由:**

- 決算カードのデータは「年度×科目の集計値」であり、個別取引の概念がない
- 複式簿記の借方・貸方構造は自治体財政の公開データには存在しない
- このモデルを残すと、新しいFiscalYearSettlementモデルとの間で「どちらがデータの正とするか」の混乱が生じる
- 既存の取引データは政治資金のもので、自治体財政には一切使わない

#### Counterpart / TransactionCounterpart

**判定: 削除**

**理由:**

- 政治資金では「取引先」を1件ずつ記録する法的要件があったが、自治体財政の公開データには取引先情報がない

#### Donor / TransactionDonor

**判定: 削除**

**理由:**

- 政治資金の寄附者（個人・法人・政治団体）を管理するモデル。自治体財政に該当する概念がない

#### OrganizationReportProfile

**判定: 削除**

**理由:**

- 政治資金収支報告書の提出プロファイル（団体正式名称、事務所住所、議員関連情報等）を保持するモデル
- 自治体のメタデータ（人口、面積等）はPoliticalOrganizationの拡張フィールドとFiscalYearSettlementで対応する

#### TransactionType / DonorType enum

**判定: 削除**

**理由:**

- `TransactionType` は複式簿記の取引種別（income, expense, offset等）。決算カードの科目体系とは無関係
- `DonorType` は寄附者種別。自治体財政に該当なし

### 新規作成: 自治体財政に必要なモデル

#### FiscalYearSettlement（年度別決算データ）

決算カードの1行（= 1自治体 × 1年度）に対応するモデル。本プロジェクトのデータの中核。

```
FiscalYearSettlement
  id
  municipalityId        → Municipality
  fiscalYear            2023

  # 歳入（款レベル、約28項目） — すべてフラットカラム・not null・default(0)
  revLocalTax           → 地方税
  revLocalTransferTax   → 地方譲与税
  revLocalConsumptionTax → 地方消費税交付金
  revLocalAllocationTax → 地方交付税
  revNationalSubsidy    → 国庫支出金
  revPrefectureSubsidy  → 都道府県支出金
  revLocalBond          → 地方債
  ...（他の歳入科目）

  # 歳出・目的別（約15項目）
  expAssembly           → 議会費
  expGeneralAdmin       → 総務費
  expWelfare            → 民生費
  expHealth             → 衛生費
  expEducation          → 教育費
  expDebtService        → 公債費
  ...（他の目的別科目）

  # 歳出・性質別（約15項目）
  expPersonnel          → 人件費
  expAssistance         → 扶助費
  expDebtServiceNature  → 公債費（性質別）
  expMaterials          → 物件費
  expConstruction       → 普通建設事業費
  ...（他の性質別科目）

  # 財政指標
  fiscalPowerIndex      → 財政力指数
  currentBalanceRatio   → 経常収支比率
  realBalanceRatio      → 実質収支比率
  realDebtServiceRatio  → 実質公債費比率

  # ストック情報
  reserveFundBalance    → 積立金現在高
  localBondBalance      → 地方債現在高

  # メタデータ（年度ごとに変動）
  population            → 人口（1人あたり換算・経年比較に使用）
  similarGroupCode      → 類似団体区分

  # 取り込み管理
  dataSource            "e-stat" | "decision-card" | "manual"
  createdAt, updatedAt

  @@unique([municipalityId, fiscalYear])
```

**設計判断: 歳入・歳出の格納方法 → フラットカラムを採用**

決算カードは全自治体統一フォーマットであり、科目が安定している（該当なしの科目は0円、nullは発生しない）。この特性から、通常のカラムで全項目を網羅する方式を採用する。

採用理由:
- DB側でnot null制約・型・デフォルト値を保証でき、データの整合性が堅い
- 将来の科目別比較クエリ（自治体間ランキング等）にSQLで直接対応できる
- データ量が少ない（180自治体×数年度=数百行）ため、約60カラムでもパフォーマンス上の問題はない
- 科目体系は款レベル（大分類）ではここ20年ほぼ変更がなく、マイグレーション頻度は低い

#### MunicipalityType enum（新規）

```prisma
enum MunicipalityType {
  prefecture  // 道
  city        // 市
  town        // 町
  village     // 村
}
```

## 変更の全体像

```
【維持】
  User ─── UserTenantMembership ─── Tenant

【変更】
  PoliticalOrganization
    + municipalityCode, municipalityType, population, area
    - transactions, reportProfiles, balanceSnapshots のrelation

【削除】
  Transaction, TransactionCounterpart, TransactionDonor
  Counterpart, Donor
  OrganizationReportProfile, BalanceSnapshot
  TransactionType, DonorType enum

【新規】
  FiscalYearSettlement（年度別決算データ）
  MunicipalityType enum
```

## 既存コードへの影響

### 影響が大きい箇所

| 箇所 | 影響 | 対応方針 |
|------|------|---------|
| `shared/accounting/account-category.ts` | 全面書き換え | 自治体財政の款レベル科目体系を新規定義（フェーズ1-3） |
| `admin/src/server/contexts/data-import/` | MFクラウドCSV特化のパーサー・ユースケースすべて | e-Stat CSVパーサーで置換（フェーズ1-2） |
| `admin/src/server/contexts/report/` | 政治資金収支報告書の生成ロジック全体 | 全削除 |
| `webapp/src/server/contexts/public-finance/` | Transactionベースのrepository/usecase | FiscalYearSettlementベースに書き換え（フェーズ2-1） |

### 影響が小さい（再利用可能な）箇所

| 箇所 | 理由 |
|------|------|
| `SankeyData` 型・Sankeyコンポーネント | データ形状（nodes + links）はドメイン非依存 |
| `CategoryAggregation` パターン | 歳入・歳出のカテゴリ別集計ロジックは構造が類似 |
| loader/usecase/repositoryのアーキテクチャパターン | レイヤードアーキテクチャの枠組みはそのまま踏襲 |
| admin UIの認証・テナント管理 | ドメイン非依存 |
