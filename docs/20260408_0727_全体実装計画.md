# 全体実装計画

## 目的

**北海道の住民が**、自分のまちの財政状況を「気軽に見て、理解し、共有し、当事者意識を持てる」状態になるため。

現在のコードベースは政治資金可視化アプリ（marumie）をベースにしているが、データモデル・歳入歳出の科目体系・サイト文言のすべてが政治資金の文脈であり、自治体財政データを表示できる状態にない。本計画は、何をどの順序で実装すれば最短で「北海道の自治体の財政データが住民に見える」状態に到達できるかを定義する。

---

## 現状分析

### コードベースの状態

| 領域 | 状態 | 詳細 |
|------|------|------|
| データモデル | 政治資金専用 | Transaction（個別取引・複式簿記）、Counterpart、Donor等。年度×科目の集計値を保持する構造がない |
| 歳入歳出の科目体系 | 政治資金専用 | `account-category.ts`に収入12カテゴリ・支出10カテゴリ（寄附、交付金、パーティー等） |
| データ取り込み | 政治資金専用 | admin data-importコンテキストがMFクラウドCSVの取り込みに特化 |
| UI（サンキー図等） | **再利用可能** | SankeyData型を受け取る設計。データの入口（loader/usecase）を差し替えれば流用可能 |
| サイト文言 | 政治資金の文脈 | メタデータ、ExplanationSection、Footer、AboutSection等がすべて政治資金の文言 |
| 決算カードパーサー | **未実装** | コード上に一切存在しない |

### 現データモデルと決算カードの構造的差異

| 項目 | 現モデル（Transaction） | 決算カード |
|------|----------------------|-----------|
| データの粒度 | 個別取引（1件ずつ） | 年度×科目の集計値 |
| 記帳方式 | 複式簿記（借方・貸方） | 単一科目の期末値 |
| 科目体系 | 政治資金規正法の様式 | 地方財政法に基づく全国統一分類 |
| 時間軸 | 取引日（日次） | 会計年度（年次） |

この差異から、**既存のTransactionモデルに決算カードデータを押し込むのは不適切**であり、自治体財政データ用の新しいデータモデルが必要となる。

## フェーズ構成

```
フェーズ0: サイトの自治体財政コンテキスト化
  ↓
フェーズ1: データ基盤の構築（データモデル＋パーサー＋取り込み）
  ↓
フェーズ2: コア可視化機能（サンキー図・サマリー・用語平易化）
  ↓
フェーズ3: 訴求力強化（財政指標・1人あたり換算・経年変化・OGP）
```

### 依存関係図

```

                                                            │
フェーズ1（データ基盤）────────────────────────────────────── │

  ├─ 1-2: 決算カードExcelパーサー or e-Stat CSVパーサー       │
  ├─ 1-3: 自治体財政用の歳入歳出科目体系定義                      │
  └─ 1-4: adminデータ取り込み画面（パーサー＋インポート）      │
                  │                                          │
                  ▼                                          ▼
フェーズ2（コア可視化）──── フェーズ0とフェーズ1の両方が前提
  ├─ 2-1: webappのloader/usecase差し替え（SankeyData生成）
  ├─ 2-2: 用語の平易化（friendly-term-map）
```

## フェーズ0: サイトの自治体財政コンテキスト化

### 目的

サイト全体の文言・メタデータを自治体財政の文脈に更新し、プロジェクトの方向性を確定する。ロジック変更を伴わない静的な文言差し替えのため、データ基盤構築と並行して着手できる。

### 対象箇所

| 対象 | 変更内容 |
|------|---------|
| `webapp/src/app/layout.tsx` | メタデータ（title, description, OGP）を「自治体財政まる見え」に変更 |
| `ExplanationSection.tsx` | 政治資金の説明文 → 自治体財政プロジェクトの説明・データ出典・免責事項 |
| `Footer.tsx` | 「寄附で応援」「党員になる」等のリンク削除、CivicTechEzo関連リンクに更新 |
| AboutSection | 「チームみらいについて」→「CivicTechEzoについて」 |
| TransparencySection | 文言を自治体財政の文脈に変更 |
| `page.tsx`のgenerateMetadata | `${org.displayName} - 自治体財政まる見え` |
| CashFlowSection | 「未登録の政治団体」→「未登録の自治体」等 |
| `robots.ts`, `sitemap.ts` | URL・サイト名の更新 |

### 前提条件

なし（他フェーズと独立）

## フェーズ1: データ基盤の構築

### 目的

決算カード（またはe-Stat）のデータを取り込み、webapp側で利用できるようにする。プロジェクトの**最大のボトルネック**であり、ここが完了しないとフェーズ2以降のすべてが着手できない。

### 1-1: 自治体財政データモデル設計

既存のTransactionモデル（個別取引ベース）では決算カードの集計データを表現できないため、新しいモデルを設計する。

**設計上の判断ポイント:**

- 既存のPoliticalOrganizationモデルを自治体エンティティとしても使うか、新たにMunicipalityモデルを作るか
  - PoliticalOrganizationには既にslug、displayName、tenantIdがあり、サンキー図のloader等がこのモデルに依存している
  - 人口（population）、面積等のフィールドを追加すれば拡張可能だが、「政治団体」と「自治体」の概念を1モデルに混在させることになる
- 決算カードの集計値を保持するモデル（例: FiscalYearBudget, BudgetItem等）の設計
  - 歳入・歳出の科目別金額（款レベル）
  - 財政指標（財政力指数、経常収支比率等）
  - 人口・面積等のメタデータ
  - 類似団体平均値

**新規Bounded Context候補:**

| コンテキスト | 責務 |
|-------------|------|
| webapp: `municipal-finance` | 自治体財政データの公開・可視化（既存public-financeの自治体財政版） |
| admin: `fiscal-data-import` | 決算カード/e-Statデータの取り込み・管理 |

既存の`public-finance`コンテキストを拡張するか、新コンテキストを作るかは詳細設計時に判断する。

### 1-2: 決算カードパーサー

**データソースの選択:**

| 選択肢 | メリット | デメリット |
|--------|---------|-----------|
| 決算カードExcel | 類似団体平均値が含まれる、1ファイルで全市町村 | Excelパース処理が複雑 |
| e-Stat CSV | 機械可読で取り込みが最も容易 | 類似団体平均値が含まれない |

推奨: **Phase 1ではe-Stat CSV**を採用し取り込みコストを最小化する。類似団体比較が必要になるフェーズ3以降で決算カードExcelパーサーを追加する。

**パーサーの責務:**

- CSV/Excelファイルの読み込み・パース
- 自治体財政用の歳入歳出科目体系へのマッピング
- ドメインモデルへの変換
- バリデーション（必須項目チェック、数値整合性等）

### 1-3: 自治体財政用の歳入歳出科目体系

既存の`account-category.ts`（政治資金）に相当する、自治体財政の科目分類を定義する。

**歳入の科目体系（款レベル）:**

地方税、地方譲与税、各種交付金、地方交付税、国庫支出金、都道府県支出金、地方債、その他（分担金・使用料・手数料・財産収入・寄附金・繰入金・繰越金・諸収入）

**歳出の科目体系:**

- 目的別: 議会費、総務費、民生費、衛生費、農林水産業費、商工費、土木費、消防費、教育費、公債費、その他
- 性質別: 人件費、扶助費、公債費、物件費、維持補修費、補助費等、普通建設事業費、その他

### 1-4: adminデータ取り込み画面

既存のdata-importコンテキスト（MFクラウドCSV取り込み）を参考に、決算カード/e-Statデータの取り込みフローを実装する。

**取り込みフロー:**

1. ファイルアップロード（CSV or Excel）
2. パース・プレビュー表示
3. バリデーション結果の確認
4. インポート実行
5. 取り込み結果の確認

**対象年度・自治体の管理:**

- 北海道内179市町村＋道
- 直近2〜3年度分を初期データとして取り込み

## フェーズ2: コア可視化機能

### 目的

取り込んだ決算カードデータを、住民が「見てわかる」形で表示する。既存のUIコンポーネント（サンキー図、FinancialSummary等）を活かしつつ、データの入口を自治体財政データに差し替える。

### 2-1: loader/usecase差し替え

**既存の流れ:**
```
page.tsx → loadTopPageData → usecase（SankeyData生成等） → repository → Transaction
```

**新しい流れ:**
```
page.tsx → loadTopPageData → usecase（SankeyData生成等） → repository → 自治体財政データモデル
```

既存のSankeyData型・UIコンポーネントはそのまま利用し、usecase/repositoryレベルで自治体財政データモデルからSankeyData型への変換ロジックを実装する。

**変更対象のusecase:**

| usecase | 変更内容 |
|---------|---------|
| サンキー図生成 | 自治体財政の歳入→歳出フローを生成（目的別 or 性質別の切替対応） |
| 財務サマリー | 歳入総額・歳出総額・収支を自治体財政データから計算 |
| 月次集計 | 決算カードは年次データのため、月次は非表示にするか別の表示に変更 |
| 残高シート | 自治体の積立金・地方債残高に対応、またはセクション自体を差し替え |

### 2-2: 用語の平易化

`friendly-term-map.ts`を新規作成し、自治体財政の専門用語を日常的な言葉に変換するマッピングを定義する。

適用箇所: サンキー図のノードラベル、FinancialSummaryCard、取引一覧のカテゴリ名

詳細は `docs/20260329_1457_CivicTechEzo価値観に沿った機能拡充設計.md` の施策2を参照。

### 2-3: ひとことサマリー

ダッシュボード最上部に、財政データを自然言語で1〜2文に要約したカードを表示する。テンプレートベースで、SankeyDataから数値を抽出して埋め込む。

詳細は同設計書の施策1を参照。

## フェーズ3: 訴求力強化

### 目的

コア可視化の上に、住民の「気づき→共有→当事者意識」を促す機能を追加する。

### 3-1: 財政危機訴求指標（第1群）

決算カードから取得可能な指標のうち、最もインパクトが大きい3つを実装する。

| 指標 | 可視化 |
|------|--------|
| 住民1人あたり借金 vs 貯金（C4） | 天秤バー or バランスバー |
| 義務的経費比率（B2） | 横棒バー1本 |
| 貯金×借金ハサミグラフ（C1） | 2本の折れ線（交差表現） |

詳細は `docs/20260329_1603_財政危機訴求指標と可視化設計.md` を参照。

### 3-2: 住民1人あたり換算表示

PoliticalOrganization（または自治体モデル）のpopulationフィールドを利用し、各金額を1人あたりに換算するトグルを追加する。決算カードに人口データが含まれているため、フェーズ1のデータ取り込み時に人口データも保持していれば追加のデータ取得は不要。

### 3-3: 経年変化ハイライト

複数年度のデータを比較し、大きく変化した項目を自動検出してハイライト表示する。フェーズ1で複数年度分のデータを取り込んでいることが前提。

### 3-4: SNSシェア用OGP対応

`webapp/src/app/o/[slug]/[year]/opengraph-image.tsx`を新規作成し、組織・年度ごとの動的OGP画像を生成する。

### 3-5: 財政危機訴求指標（第2群・第3群）

第1群の実装・フィードバックを踏まえて、経常収支比率の推移、人口×扶助費、類似団体比較等を追加する。類似団体比較には決算カードExcelパーサー（類似団体平均値が含まれる）が必要になるため、この段階でExcelパーサーを追加する。

## 最初に着手すべきこと

上記の依存関係から、**並行して2つの作業を開始する**のが最も効率的:

1. **フェーズ0（サイトコンテキスト化）** — ロジック変更なし・文言差し替えのみのため、すぐに着手・完了できる
2. **フェーズ1-1（データモデル詳細設計）** — フェーズ1以降すべての基盤となるため、設計を先行して確定させる

フェーズ1-1の詳細設計では、以下の判断を行う必要がある:

- PoliticalOrganizationモデルの拡張 vs 新規Municipalityモデルの作成
- 決算カード集計値を保持するモデル構造（正規化レベル、年度管理方法）
- 既存public-financeコンテキストの拡張 vs 新規コンテキスト（municipal-finance）の作成
- e-Stat CSVの具体的なフォーマット調査とパース戦略
